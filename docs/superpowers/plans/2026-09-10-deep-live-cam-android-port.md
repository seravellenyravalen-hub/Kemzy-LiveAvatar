# Deep-Live-Cam Android Port Plan

## Goal
Create a separate Android implementation of the Deep-Live-Cam live face-swap pipeline inside Kemzy while leaving the desktop environment untouched. The Android implementation must use the same conceptual processing stages: source-face preparation, live face analysis, face alignment, face swapping, post-processing/compositing, and continuous live preview/output.

## Non-goals
- Do not modify or replace the existing desktop Deep-Live-Cam environment.
- Do not copy proprietary desktop UI code into Android.
- Do not use prerecorded avatar video, frame playback, or a static-image animation shortcut.
- Do not assume Android can expose a system-wide virtual camera; capability must be detected and tested on the physical device.
- Do not automatically download large model files on first launch.

## Architecture

Desktop reference (unchanged)
→ Android-specific implementation

CameraX → frame conversion → face-analysis model(s) → source-face embedding/reference → swap-model adapter → inverse transform → mask/feather/blend → preview/output.

The Android layer owns camera capture, lifecycle, threading, model storage, memory management, rendering, and device output. Model adapters isolate tensor contracts so a compatible ONNX face detector/landmark model and an INSwapper-compatible model can be supplied without coupling the app to a single hard-coded file.

## Work sequence

1. Establish Android face-pipeline interfaces and test contracts.
2. Add source-face loading/preparation with deterministic validation.
3. Add detector/landmark model adapters and tensor preprocessing/postprocessing.
4. Add swap-model adapter for an installed compatible ONNX model and validate its input/output contract before processing.
5. Add continuous CameraX inference loop with bounded backpressure and reusable buffers.
6. Add inverse affine transformation, mask generation, feathering, and compositing into the live frame.
7. Replace the diagnostic-only result with an actual transformed preview while retaining FPS/latency/drop metrics.
8. Add device capability probing for background execution and Android virtual-camera/output support without bypassing platform security.
9. Build and test on the Infinix device at progressively lower camera resolutions until stable real-time operation is measured.
10. Only after the transformed preview is proven, test the Android output path with a consenting private test account/app.

## TDD/acceptance criteria

- Source image with no detectable face is rejected clearly.
- A valid source face produces a reusable source reference without processing every source image repeatedly.
- Detector/landmark adapters reject incompatible model tensor contracts instead of silently producing bad frames.
- Swap adapter refuses to run when the required model is absent or incompatible.
- Live processing never accumulates an unbounded frame queue.
- Every ImageProxy is closed promptly.
- Transformed output changes continuously when the camera subject moves.
- No output is generated by replaying captured frames.
- Metrics report actual inference latency, processed FPS, and dropped frames.
- Android output capability is reported honestly as available/unavailable based on the device rather than assumed.

## Model/data policy

Models are treated as external local assets. The app must not silently fetch large model files. Deep-Live-Cam's public repository is used as a behavioral/technical reference; model licensing and distribution terms must be checked before redistributing any model in an APK.

## First implementation milestone

Deliver the Android face-pipeline contracts, source-face validation, model compatibility checks, and tests. Do not label the feature as working until an actual compatible face detector and swap model are executed against live CameraX frames on the physical device.
